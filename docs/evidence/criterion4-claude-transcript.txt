**Flags:**

1. **`propose_script`/`get_proposal` for a genuinely read-only command (`uptime`) failed dry-run**, not because it's unsafe but because `/usr/bin/uptime` isn't on the read-only-safe allowlist and has no shim. That's a false negative from a safety standpoint (the script is harmless) but a true negative from an allowlist standpoint (unshimmed binary = automatic reject). Worth knowing the allowlist gates on binary identity, not actual read/write behavior — a truly read-only script can still be rejected if its binary hasn't been vetted/shimmed.
2. **Provenance field inconsistency**: `get_host_info` and `get_array_state` both return a `source` field (`procfs`, `emhttp`), but `list_containers` returns no `source`/provenance field at all — just the array. Not wrong, just an inconsistency in what "source" transparency looks like across tools.
3. **No `count` field**: `list_containers` doesn't expose a count; I had to count the array (42) myself. If your spec expects a count field, it's missing.
4. Real-host oddity (not a tool bug): array disks are named `parity`, `disk1`, `disk3`, `cache` — `disk2` is absent from the array. That's host state, not an MCP inconsistency, but flagging since it's unusual.
